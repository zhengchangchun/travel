## §0 实测定位（为什么会"像要手动点、还不全"）

自动采集**确实触发了**（网络面板可见 `/api/collect/viewport`），但**慢到看起来像没工作**：

| 实测证据 | 数值 |
|---|---|
| 一个 viewport 采集 run 的耗时 | **31 分钟**（run#31：fetch 2600） |
| 卡在 `running` 且 `fetched=0` 的 run | **12 个**（等速率令牌，饿死） |
| 单格调用预算 | 48 次 |
| 全局限流 | **60 次/分钟**（所有 run 共享一个滑动窗口） |
| 前端传的分类 | **`all`（四类一起采）** |

**算一下**：zoom 15 一个视野 ≈ 2–4 格 × **4 个分类** × 48 次 ≈ **384–768 次调用**；
按 60/分钟 ⇒ **6–13 分钟**。用户看到的就是「一直在加载、数据不涨」。

另外：**新视野会新起一个 run，旧 run 不取消** ⇒ 多个 run 抢同一个 60/分钟令牌 ⇒ 互相饿死、全部卡 `running`。

---

## §1 要做的（五条）

| 编号 | 修复 | 理由 |
|---|---|---|
| **R1** | **一次只采一个分类**（轮转） | 前端传当前筛选的分类；若筛选为「全部」，则按 `food→stay→sight→play` **轮转**，每次视野变化只采一个 ⇒ 单次调用量降到 1/4 |
| **R2** | **单飞 + 作废旧 run** | 同一 `(city, category)` 同时只允许 1 个 run；新视野到来时把旧 run 标 `superseded` 并**立即停止**（不再抢令牌） |
| **R3** | **速率上调** | `DEFAULT_VIEWPORT_RATE_PER_MIN` **60 → 180**（3 次/秒，仍保守；高德 Web 服务个人 QPS 一般 3–10），抽成常量可配 |
| **R4** | **进度可见** | 前端显示「本区域已采 x / y 格」，采到就补旗；**不要只有一句"加载中…"** |
| **R5** | **优先视野中心格** | 按格中心到视野中心的距离排序，先采中间（用户最在看的地方） |

### 期望效果

- 切到某区域放大后，**几秒到几十秒内**看到数据逐步补齐，而不是几分钟不动
- 用户**不需要点任何按钮**

- [x] R3 速率 60 → 180


实现要点：

- R1 `server/collect.js` 导出 `CATEGORY_ROTATION` / `nextCategory`；`/api/config` 暴露
  `categoryRotation`；前端 `pickCollectCategory()` 在筛选为「全部」时按 food→stay→sight→play
  轮转，单一分类筛选则直接采该类。每次视野变化只采一个分类。
- R2 `createViewportRunRegistry()` 按 `(city,category)` 单飞；新视野 `start()` 返回旧 runId，
  旧 run 写 `superseded`，`isCancelled()` 让 `collectViewport/collectCell` 在格/页边界立即停，
  被作废格不标覆盖（可重试），并释放旧格认领供新 run 接管。
- R3 `DEFAULT_VIEWPORT_RATE_PER_MIN = 180`（3 次/秒），`server/index.js` 引用该常量，
  仍走滑动窗口限流防封 key。
- R4 `/api/collect/status` 返回 `done_grids / total_grids`；前端 `#view-progress` +
  `UI.setViewProgress()` 显示「本区域已采 x / y 格」，进行中每 700ms 刷新。
- R5 `collectViewport` 按格中心到 bbox 中心距离升序排序，先采视野中心格。
