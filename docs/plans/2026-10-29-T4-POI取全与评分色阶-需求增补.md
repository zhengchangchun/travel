# T4 需求增补：POI 取全 · 分类纯净 · 评分色阶

> 2026-10-29 · 依据用户原话：「分批取，如果选择住宿的时候就全部都是住宿，尽量取全，一次取 200 个的话就分批取，
> 取到没有为止，按照评分在页面上展示颜色由浅入深」
> 前置：T1（骨架）／T2（选中·行程）／T3（路线）已交付。

---

## §0 背景

现在的三个毛病（用户实际用出来的）：

1. **列表不全** —— 单次查询被高德截到 200 条，小店铺排在 200 名开外就看不到（已有诊断，见 `docs/evidence/diagnostics/`）
2. **分类不纯** —— 选了「住宿」还可能混进别的东西
3. **看不出版本高低** —— 地图上所有旗子一样深，评分没有可视化

用户要求：**分批取、取到没有为止、选什么就全是这个分类、按评分由浅入深显示颜色。**

---

## §1 功能（本期做）

| 编号 | 功能 | 说明 |
|---|---|---|
| **J1** | **分批取全** | 不再"一次搜一个城市"，而是**按行政区逐区翻页**，每区翻到没有为止，全城去重合并 |
| **J2** | **突破 200 上限** | 单查询 200 条 → 分区后可拿到数倍（实测：杭州前 6 区去重即 **1198** 家住宿） |
| **J3** | **分类纯净** | 选「住宿」⇒ 结果 **100% 是住宿**（后端按 `typecode` 前缀严格过滤，不含混类） |
| **J4** | **采集落库 + 增量** | 取回的结果**落 SQLite 缓存**，长期复用；二次采集只补新增，不重复消耗配额 |
| **J5** | **进度可见** | 分批采集是长任务 ⇒ 要有进度（已取区数/已入库条数），不能白屏干等 |
| **J6** | **评分色阶** | 地图旗子颜色**由浅入深**按评分渐变；配图例（浅＝低分，深＝高分） |
| **J7** | **分类色相不变** | 分类仍用各自色相（美食橙/住宿蓝/景点绿/游玩紫），**色相表分类、深浅表评分** |
| **J8** | **满分特殊标识** | 评分达阈值（默认 **5.0**）的点给**金色特殊标识**：地图上金旗/金边，列表上金色星徽（阈值抽成常量，一行可改） |

### 为什么 J6+J7 这样设计

用户说"按评分由浅入深"，同时又保留了 4 个分类。两者不冲突：

```
色相(hue)  = 分类     → 一眼看出这是吃/住/玩/看
深浅(light) = 评分     → 一眼看出这家好不好
```

选「住宿」时全是同一色相 ⇒ 深浅差异特别明显，正好达到用户要的效果。

## §2 取数策略（分批取全）

### 分片维度：行政区

`GET /v3/config/district?keywords=<城市>&subdistrict=1` 拿到下辖区县（**杭州 13 个**：上城/拱墅/西湖/滨江/萧山/余杭/临平/钱塘/富阳/临安/桐庐/淳安/建德）。

然后 **逐区 × 逐页**：
```
for 区 in 城市的所有区县:
    for 页 in 1..8:                 # 单查询上限 200 = 25×8
        结果 = place/text(keywords=分类词, city=区的adcode, types=分类码, page=页)
        if 结果为空: break          # ← 「取到没有为止」
        合并（按 poi_id 去重）
```

### 二级分片（区取满 200 条时）—— **必做，不是兜底**

用户明确要求：「**每次 200 的话 就继续分页**」。

若某区取满 200（说明该区被截断），**必须继续分片**，直到没有为止。做法（按优先级）：

1. 把该区按**中心向外的小半径周边搜索**切开（半径 3000/1500/800/400/200 米逐级缩小），每个子片再翻页到 200
2. 或按**多边形搜索**（`place/polygon`）把该区切成若干小块
3. 子片内若仍取满 200 → 继续对半缩小半径，**递归到没有为止**

**验收硬指标**：对一个取满 200 的区，最终入库条数必须 **> 200**。

### 分类纯净

归一化时**只保留** `typecode` 前缀匹配该分类的 POI（住宿 `100000`…、美食 `050000`…）。
不匹配的**直接丢弃**，不入库。

## §3 数据模型（新增缓存表）

```sql
CREATE TABLE IF NOT EXISTS pois (
  poi_id     TEXT PRIMARY KEY,          -- 高德 POI id
  city       TEXT NOT NULL,             -- 城市名（如「杭州」）
  adcode     TEXT,                      -- 所属区县 adcode
  category   TEXT NOT NULL,             -- food / stay / sight / play
  name       TEXT NOT NULL,
  address    TEXT,
  lng        REAL NOT NULL,
  lat        REAL NOT NULL,
  typecode   TEXT,
  rating     TEXT,                      -- 评分（可能为空）
  cost       TEXT,                      -- 人均
  tel        TEXT,
  photo      TEXT,
  fetched_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_pois_city_cat ON pois(city, category);
CREATE INDEX IF NOT EXISTS idx_pois_city_rating ON pois(city, category, rating);
```

**采集元数据**（记录每个 (城市,分类) 的采集状态，供进度与增量用）：

```sql
CREATE TABLE IF NOT EXISTS poi_collect_runs (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  city        TEXT NOT NULL,
  category    TEXT NOT NULL,
  started_at  TEXT NOT NULL,
  finished_at TEXT,
  status      TEXT NOT NULL DEFAULT 'running',   -- running / done / failed / partial
  n_fetched   INTEGER NOT NULL DEFAULT 0,        -- 高德返回条数（含重复）
  n_inserted  INTEGER NOT NULL DEFAULT 0,        -- 新入库
  n_updated   INTEGER NOT NULL DEFAULT 0,
  detail      TEXT                               -- JSON：逐区进度
);
```

> ⚠️ 这两张表是**幂等迁移**（`CREATE TABLE IF NOT EXISTS`），旧库启动时自动补。

## §4 接口契约（新增）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/collect` | 触发采集 `{city, category}`（`category` 省略＝全部 4 类）；**立即返回 runId**，后台跑 |
| GET | `/api/collect/status?runId=` | 进度：`{status, n_inserted, n_fetched, done_districts, total_districts, percent}` |
| GET | `/api/collect/runs?city=` | 该城各分类的历史采集状态（最后采集时间、条数） |
| GET | `/api/pois?city=&category=&sort=rating\|default&limit=&offset=` | **从缓存读**（不打高德）：`{total, items:[…]}`，`sort=rating` 按评分降序 |
| GET | `/api/pois/stats?city=` | 各分类已收录条数 + 评分分布（供色阶图例用） |

- 采集是**长任务**：必须后台跑 + 进度可查（用户不能干等）
- `POST /api/collect` 对同一 (城市,分类) 正在跑时 → `409`
- 采集**失败逐区容错**：某区失败记 warning 继续，最后 `status=partial`，不整轮失败

## §5 视觉：评分色阶

- **色阶映射**：评分 → 明度
  | 评分 | 效果 |
  |---|---|
  | 无评分 | 最浅 + 灰色描边（"信息不足"） |
  | 3.0 | 浅 |
  | 4.0 | 中 |
  | 4.5 | 深 |
  | 5.0 | 最深 |
- 具体：把分类的基准色转 HSL，`L` 从 `72%`（浅）线性映射到 `34%`（深），按评分在 `[3.0, 5.0]` 内归一
- **图例**：地图角落一条色阶条，「浅 ← 评分 → 深」，标注 3.0 / 4.0 / 5.0
- **满分特殊标识（J8）**：评分 ≥ 常量 `TOP_RATING`（默认 `5.0`）的点：
  - 地图：旗子加**金色描边 + 星徽**（独立于色阶之外的一层，优先级最高）
  - 列表：名称旁一个**金色星徽**
  - 图例里单列一项「★ 满分」
- 选中态（T2 的 ★）与色阶/满分标识**不冲突**：选中用「加白边 + 放大」，不改颜色

## §6 配额与成本（必须让用户知道）

- 一次全量采集一个城市的一个分类 ≈ **13 区 × ~8 页 ≈ 100 次**高德调用
- 四个分类合计 ≈ **400 次/城市**
- 高德个人开发者免费额度有限（以控制台「配额管理」为准）⇒ 因此：
  - **必须落库缓存**，不重复采集
  - **必须支持增量**（二次采集只补新增）
  - 前端要显示「已收录 N 条 / 上次采集时间」，让用户知道什么时候该刷新
