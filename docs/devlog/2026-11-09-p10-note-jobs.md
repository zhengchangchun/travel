## 改法：长任务走后端任务表

| 层 | 改前 | 改后 |
| --- | --- | --- |
| 接口 | `POST /api/notes/discover`、`/fetch`、`/:id/refresh`（同步，一直挂着） | 新增 `POST /api/notes/jobs`（起任务，立刻回 id）＋ `GET /api/notes/jobs/:id`（状态/阶段/已用毫秒）＋ `POST …/cancel`；**旧的同步接口保留**，与任务走同一份实现（`discoverItems` / `fetchAndIngest` / `refreshNoteById`） |
| 进度 | 无 | 抓取器在 stdout 吐 `#progress <阶段>` 行（不参与结果解析，结果仍取最后一行 JSON），服务端按行收下当 `stage` |
| 取消 | 无 | 任务表存子进程句柄，取消 = 立刻 kill；取消后**不再重试**、结果**永不采用** |
| 并发 | 两次搜索互相覆盖状态栏 | 同 `kind+platform` 新的顶掉旧的（两个浏览器抢同一个登录 profile 会双双失败）；前端还有 `st.job` 守卫，过期回调一律丢弃 |
| 界面 | 只有一行「搜「x」中…（10–25 秒）」 | 「搜「x」：已 N 秒 · 当前阶段」+ 右侧「取消」按钮（只在跑的时候出现） |

覆盖到 4 个入口：**搜笔记 / 粘链接抓取 / 候选「存到本地」/ 详情「重抓」**（都是同一种长活）。
前端 6 分钟兜底：超过就把服务端任务也取消掉，按 TIMEOUT 报人话。

## 踩到的两个坑

1. **杀子进程不等于杀掉浏览器**：子进程是 `node pw.cjs`，它下面还有 Chromium（持着登录 profile）。
   只 `child.kill()` ⇒ Chromium 变孤儿占着 profile，下一次抓取会栽在「profile 被占用/登录态读不到」。
   修法＝`spawn(..., { detached: true })` 自成进程组，取消/超时按**进程组**杀（`process.kill(-pid)`），
   无 pid（测试里的假 child）或已退出时退回单杀。实测：取消后 `ps` 里 `xhs-main` 的进程数 = 0，且紧接着再搜一次正常返回 10 条。
2. **任务表要自己收敛**：`finished_at` 过了 TTL 就删（`get` 时顺手 sweep），并且 `start` 里加完任务再 sweep 一次 ⇒ 数量不会超过 `maxJobs`。
